## 1. 背景与目标

魔方收入里有一批**数量固定、按周期重复**的来源：日常任务、周常任务、每月签到、世界巡游。
现在（以及 #17 规划的通用录入）都要手工选事件、填数量、填时刻——每天至少 3 笔、每周再加 3 笔，重复且易漏。

**目标**：把这批固定来源做成「任务看板」——点一下即完成并自动记账，点错了双击取消；
周期到了自动复位；同一周期内不允许重复完成。

**非目标**（本期不做）：

- 世界巡游等级本身的进度管理（只记录里程碑领取，不追踪 PT/等级）
- 红尖尖的同类看板（2026-10-24 已由 #31 扩展，见 `docs/20261024_红尖尖固定来源方案.md`）
- 其它非固定来源的录入（活动建造、礼包等，仍走 #17 的手工录入）

### 2.1 历史台账的实际情况（库里已导入的明细）

| 来源事件 | 笔数 | 金额分布 | 实际频率 | 结论 |
| --- | --- | --- | --- | --- |
| 日常任务 | 2195 | 1×1462、2×730（个别 3/6 为聚合笔误） | 720 天为 3 笔/天，合计 4 个魔方 | 每笔对应一个子任务：1 + 1 + 2 |
| 周常任务 | 309 | 3×206、6×103 | 103 周 × 3 笔，合计 12 个魔方/周 | 3 + 3 + 6 |
| 每日签到 | 95 | 3/6/9/12 各约 24 笔 | 22 个月为 4 笔/月 | 每档一笔，合计 30 个魔方/月 |
| 世界巡游 | 89 | 5×47、7×20、8×21、27×1 | 约 11 期 × 8 档 | 5/7/5/8/5/7/5/8，合计 50 个魔方/期 |

**关键结论（直接决定方案）**：

1. 历史记录已经**按子任务/里程碑逐笔记录**，不是记汇总数 —— 任务看板可以 1:1 映射到明细，不会改变统计口径。
2. 存在**集中补录**：如 2026-08-03 一天补了世界巡游 6 档、同一天多笔时刻相同 —— 所以「补录」与「手填时刻」是刚需。
3. 存在**聚合笔误**（日常任务出现 3/6、巡游出现 27），说明靠人工填数容易出错；任务看板用固定奖励值可以从根上消除这类错误。

### 2.2 `task_status` 表（历史遗留）

```sql
CREATE TABLE task_status (
  task_id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_typ STRING,            -- 仅"日常任务"/"周常任务"
  task_name STRING,
  statu INTEGER DEFAULT 0,
  task_lasttime DATETIME NOT NULL DEFAULT "2025-09-10 00:00:00"

```

现有 6 行（3 日常 + 3 周常），`statu` 全为 0，`task_lasttime` 全是默认值。

**问题**：没有奖励值、没有周期键（无法表达"哪一天/哪一周完成"）、没有与明细的关联，
无法支撑取消完成与重复检测；且缺签到与巡游两类。

**建议**：`task_status` 清退（DDL 留档），用 §6 的新表替代。

### 3.5 「两个大类」的理解

你提到"固定两个大类"，但列了三组。从**交互形态**看实际只有两种组件：

| 组件范式 | 适用于 | 特征 |
| --- | --- | --- |
| **固定槽位型** | 日常 3 项、周常 3 项、签到 4 项 | 数量固定的一组开关，按周期整体复位 |
| **里程碑型** | 世界巡游 8 项 | 一条按等级递增的轨道，按「期」复位，可一次补多档 |

本方案按 **3 个分组（任务 / 签到 / 月卡）+ 2 种组件范式** 设计；若你说的"两个大类"是别的划法（例如把签到并入任务类），只需调整分组展示，数据模型不变。见 §13 Q-01。

## 4. 概念模型

| 概念 | 定义 |
| --- | --- |
| 任务定义 | 18 条固定数据（编码、名称、分组、周期类型、奖励、写入明细时用的来源名） |
| 周期键 `period_key` | 标识"哪一天/哪一周/哪一月/哪一期" |
| 完成记录 | 某任务在某周期已完成的证据；与一笔魔方收入明细一一对应 |
| 期初对齐 | 上线时把当期**已经手工记录过**的明细接管为完成记录，避免重复记账 |

**周期键格式**

| 周期类型 | 格式 | 示例 | 复位规则 |
| --- | --- | --- | --- |
| 天（day） | `yyyy-MM-dd` | `2026-10-17` | 换日即新周期（00:00） |
| 周（week） | `yyyy-Www`（ISO 周） | `2026-W42` | 周一 00:00 |
| 月（month） | `yyyy-MM` | `2026-10` | 自然月 1 日 00:00 |
| 期（cruise） | `yyyy-MM`（期起始月） | `2026-10` 表示 `10-01 ～ 11-30` | 每 2 个自然月一期，起点为偶数月 1 日 00:00 |

> 巡游期起点算法：`start_month = month - (month % 2)`；若结果为 0 则取上一年 12 月。
> 例：10 月 → `2026-10-01 ~ 2026-11-30`；12 月 → `2026-12-01 ~ 2027-01-31`；1 月 → `2025-12-01 ~ 2026-01-31`。
> 月键与期键字符串可能相同（都是 `2026-10`），但分属不同任务集合，唯一约束 `(task_code, period_key)` 不会冲突。

## 5. 交互需求

### 5.1 布局

```
┌─ 魔方任务看板 ─────────────────────────────────────────────────┐
│ 记账日期 [2026-10-17 ▾]   今日任务 4/4   +4 个魔方   [刷新]    │
│                                                               │
│ ┌ 日常任务（每天 4 个）────────────────────────────────────┐  │
│ │ [✔ 获得3次战斗胜利 +2] [✔ 建造舰船1次 +1] [ 通关困难 +1] │  │
│ └───────────────────────────────────────────────────────────┘  │
│ ┌ 周常任务（每周 12 个）───────────────────────────────────┐  │
│ │ [✔ PT150 +3] [✔ PT350 +3] [ PT750 +6]                    │  │
│ └───────────────────────────────────────────────────────────┘  │
│ ┌ 每月签到（每月 30 个）───────────────────────────────────┐  │
│ │ [✔ 签到1 +3] [✔ 签到2 +6] [ 签到3 +9] [ 签到4 +12]       │  │
│ └───────────────────────────────────────────────────────────┘  │
│ ┌ 世界巡游（每期 50 个）───────────────────────────────────┐  │
│ │ 5✔ ─ 15✔ ─ 25✔ ─ 35✔ ─ 45☐ ─ 55☐ ─ 65☐ ─ 75☐            │  │
│ │ 本期已领 36/50 个魔方                                      │  │
│ └───────────────────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────────────────┘
```

- 每个任务是一个**可勾选卡片**：名称 + `+奖励`，已完成显示 ✔ 并置灰。
- 各分组标题带「合计」与「已获得/应得」，方便一眼核对（每日 4、每周 12、每月 30、每期 50）。
- 顶部「记账日期」决定周期与写入明细的时刻，默认今天；**改日期即为补录**。

### 5.2 点击语义（核心）

| 操作 | 目标状态 | 行为 |
| --- | --- | --- |
| **单击**未完成任务 | 未完成 → 已完成 | 写入一笔收入明细；按钮变 ✔ 且置灰；合计与看板刷新 |
| **单击**已完成任务 | 已完成 | **无操作**（"完成后禁用"指的就是这一条，不是 `setEnabled(False)`） |
| **双击**已完成任务 | 已完成 → 未完成 | 二次确认后删除对应明细；按钮恢复可点 |
| **双击**未完成任务 | 未完成 → 已完成 | 等效于单击完成（第一次点击已生效，第二次落在已完成状态被忽略）。**不做"双击撤销"**，否则单/双击要靠延时判定，反而拖慢每次完成 |

> 实现注意：**不能用 `setEnabled(False)`**——控件被禁用后收不到鼠标事件，双击取消就没法实现。
> 正确做法是保持控件可用、用样式表达"已完成/置灰"，单击时对已完成项直接 return。
> Qt 在双击时会先派发一次 `clicked`（此时状态已是"已完成"，被忽略），随后派发 `doubleClicked`，
> 所以"已完成项单击不动作"这一条同时解决了双击误触发完成的问题。

### 5.3 取消完成的确认

删除一笔已入账的明细属于破坏性操作，需要二次确认：

> 取消「日常任务·建造舰船 1 次」的完成状态？
> 将删除 2026-10-17 21:35:12 的 1 个魔方收入记录。

### 5.4 补录

- 顶部日期切到过去某天 → 看板切换到该天的周期，可勾选当天任务；
- 世界巡游常一次补多档，允许在**同一期**内连续勾选多个里程碑；
- 记账时刻默认 = 所选日期 + 当前时分秒（可在确认框里改到分钟，避免一天多笔时刻完全一样）。

### 5.5 重复检测

三层防护：

1. **数据库唯一约束** `UNIQUE(task_code, period_key)`——最终防线；
2. **UI 状态**：已完成项单击无效；
3. **写入前校验**：同一周期已存在完成记录 → 拒绝并提示「本期已完成，双击可取消」。

## 6. 数据模型（草案）

```sql
-- 任务定义：18 条固定数据，随迁移脚本初始化
CREATE TABLE IF NOT EXISTS cube_task (
    code        TEXT PRIMARY KEY,
    grp         TEXT NOT NULL CHECK (grp IN ('daily', 'weekly', 'signin', 'cruise')),
    name        TEXT NOT NULL,
    reward      INTEGER NOT NULL CHECK (reward > 0),
    period_type TEXT NOT NULL CHECK (period_type IN ('day', 'week', 'month', 'cruise')),
    category    TEXT NOT NULL,          -- 写入明细时的来源名：日常任务/周常任务/每日签到/世界巡游
    sort_order  INTEGER NOT NULL DEFAULT 0,
    active      INTEGER NOT NULL DEFAULT 1
);

-- 完成记录：一条记录对应一笔魔方收入
CREATE TABLE IF NOT EXISTS cube_task_completion (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    task_code      TEXT NOT NULL REFERENCES cube_task(code),
    period_key     TEXT NOT NULL,
    completed_at   TEXT NOT NULL,        -- yyyy-MM-dd HH:mm:ss，可手填
    transaction_id INTEGER,              -- 关联的 resource_transaction.id；NULL 表示仅标记（历史已记账）
    created_at     TEXT NOT NULL DEFAULT (datetime('now', 'localtime')),
    UNIQUE (task_code, period_key)
);

CREATE INDEX IF NOT EXISTS idx_cube_task_completion_period
    ON cube_task_completion (period_key);
```

**为什么单独建表、不复用 `resource_transaction`**：明细只记录"钱"，任务记录需要"周期键 + 任务编码 + 与明细的关联"，
靠明细字段反推周期既脆弱又无法表达"仅标记不记账"的历史对齐场景。

**是否复用 `task_status`**：不复用（缺周期键与关联字段），清退并留档。

## 7. 写入与一致性规则

### 7.1 完成（单击）

同一事务内：

1. 计算 `period_key`（按记账日期）；
2. 校验 `(task_code, period_key)` 不存在；
3. 写入 `resource_transaction`：
   - `resource_type='cube'`、`direction='income'`
   - `record_time` = 记账时刻（默认当前，可在确认框调整）
   - `category` = 任务定义里的 `category`（沿用历史事件名，见 §8）
   - `amount` = 任务奖励
   - `note` = 任务名（如「日常任务·建造舰船 1 次」）
4. 写入 `cube_task_completion`，回填 `transaction_id`；
5. 更新该日 `resource_daily.last_record_time`（若该日已有行则取较晚者，没有则新建 detail 行）。

### 7.2 取消（双击）

同一事务内：

1. 找到完成记录；
2. 若 `transaction_id` 存在且明细仍存在 → 删除该明细；否则跳过（说明已被手工删除）；
3. 删除完成记录（硬删除，释放唯一约束）；
4. 重算该日 `last_record_time`（等于该日剩余明细的 `MAX(record_time)`，无明细则置 NULL）。

### 7.3 孤儿处理（明细被外部删除）

用户在 #17 的通用列表里删掉了任务明细时：
- 完成记录还在，但 `transaction_id` 指向的明细已不存在；
- 读取时左连接检测：**若关联明细缺失，视为"未完成"并在 UI 上标注**（例如 ⚠ 图标 + tooltip「关联记录已不存在」）；
- 用户可单击重新完成（会重建明细并更新关联），或双击把残留记录清掉。

### 7.4 期初对齐（上线时的一次性处理）

上线当期（当天/本周/本月/本期）很可能已经有手工记录的明细。若不处理，用户第一次点看板就会**重复记账**。

推荐方案 **A**（推荐）：

- 上线时跑一次性脚本，扫描当期已有明细，按「类别 + 金额」匹配到任务，生成完成记录并关联原明细；
- 金额有重复的（世界巡游 5/7/8 有重复）按时间顺序就近匹配；
- 匹配结果输出一份报告，供人工核对。

备选：

- **B**：看板从**下一个周期**开始生效（当期显示"本期已结束/未纳入"），不做对齐；
- **C**：手工「仅标记不记账」（`transaction_id = NULL`），需要额外的 UI 入口，不推荐，容易误用。

## 8. 统计口径

**沿用历史事件名，签到类做一次改名**：写入明细时 `category` 用「日常任务 / 周常任务 / **每月签到** / 世界巡游」，
任务名放 `note`。理由：

- 日常、周常、巡游与历史完全一致（2195 + 309 + 89 笔），统计不分裂；
- 历史签到用的是「每日签到」（95 笔，实际是每月 4 档、金额 3/6/9/12），与本次需求用词「每月签到」不符。
  上线时把这 95 笔的 category 一并改为「每月签到」并同步字典 —— 语义修正，金额、日期、明细条数都不变，
  改名后统计仍是一条线（改名前后各期可在迁移报告里对照）；
- 不使用细粒度 category（如「日常任务·建造舰船1次」）：那会让历史数据必须重写，且 `resource_category` 膨胀到 20+ 条。

**汇总校验**（可与任务定义互相验证）：

| 周期 | 应得合计 | 公式 |
| --- | --- | --- |
| 每日 | 4 | 2 + 1 + 1 |
| 每周 | 12 | 3 + 3 + 6 |
| 每月 | 30 | 3 + 6 + 9 + 12 |
| 每期（巡游） | 50 | 5+7+5+8+5+7+5+8 |

### 10.1 布局约束（首版踩坑后的硬性要求）

首版把完整任务名直接塞进按钮，按钮 `sizeHint` 被撑到 **1848×741**，而页签可用区只有 984×614，
结果卡片被压成细条、"完全无法操作"。以下约束固化为实现要求：

| 约束 | 说明 |
| --- | --- |
| 卡片用短标签 | `cube_task.short_name`（如「战斗×3」「PT 150」「5 级」），完整任务名只进 tooltip |
| 单行卡片 | 高度固定 38～44px，不再换行；长名字不会撑高整行 |
| 分组铺满网格 | 四个同级分组用 `QGridLayout`：宽度 ≥ 940px 两列、否则单列；分组与卡片 `Expanding`，右边缘对齐不留缺口 |
| 行内等高 | 同一行的分组高度一致，内容垂直居中，避免短分组底部留白 |
| 整页竖向滚动 | 「资源统计」容器套 `QScrollArea`，内容高于窗口时滚动，而不是压扁控件 |
| 控件宽度封顶 | `QDateTimeEdit` 的 `minimumSizeHint` 约 300px，date/time 控件必须设最大宽度，否则一行就 750px+ |
| 长文本换行 | 需求经验等长文案启用 `setWordWrap(True)` |
| 不要用 Ignored 策略 | `QSizePolicy.Ignored` 会让布局把列宽压到小于控件最小宽度，控件互相重叠 |

验收：1024×768 与 800×600 下卡片完整、只有竖向滚动条、无横向滚动；
1024 及以上为两列铺满（分组右边缘对齐），800 为单列铺满。
