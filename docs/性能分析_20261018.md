# 性能分析（2026-10-18）

> 触发问题：点击「指挥官等级」卡打开指级经验窗口后，**关闭时有明显延时**（体感 1～4 秒）。
> 结论：不是渲染问题，是主线程上重复做了 3 轮「全量快照换算」，每轮 524 次 SQLite 建连。

---

## 1. 定位方法

在 offscreen 模式下构造完整 `MainWindow`，用 `time.perf_counter()` 包住
`QDialog.close()`，并逐个包装服务方法统计调用次数与耗时；另外用 `sqlite3.connect`
的计数包装统计每次操作打开了多少连接。

复现脚本的核心结构（临时脚本，不入库）：

```python
calls = {}
def timed(name):
    def deco(func):
        def wrapper(*args, **kwargs):
            start = time.perf_counter()
            try:
                return func(*args, **kwargs)
            finally:
                entry = calls.setdefault(name, [0, 0.0])
                entry[0] += 1
                entry[1] += (time.perf_counter() - start) * 1000
        return wrapper
    return deco
```

## 2. 修复前

```
open:  24.4 ms
close: 3770.6 ms

close 期间的调用统计：
  StatisticsPanel.updateCommanderStats        2 次   3766.87 ms
  CommanderService.getExpEfficiency           6 次   3757.89 ms     ← 每次约 626 ms
  CommanderService.getExpEfficiencyText       2 次   1189.05 ms
  CommanderService.getCommanderLevelCardTooltip 2 次 1262.20 ms
  CommanderService.getExpEfficiencyTooltip    2 次   1310.90 ms
```

### 2.1 根因一：等级基准没有缓存

`getExpEfficiency()` 要为 524 条快照换算绝对经验，而 `getAbsoluteExp()` 每条都要
`cumulative_exp(L-1)`；`getLevelRequirement()` 当时**没有任何缓存**，每次都走
`CommanderRepository.findLevelExp()` → `DatabaseConnection.executeQuery()` →
**新建一个 SQLite 连接**（约 1.2 ms）。

→ 单次效率计算 = 524 次建连 ≈ 626 ms。

### 2.2 根因二：一次刷新算三遍

`updateCommanderStats()` 依次取：等级卡文本、等级卡提示（内含升级预估）、效率卡文本、效率卡提示，
其中三处各自调用一次 `getExpEfficiency()`。

### 2.3 根因三：关闭时刷新两次

`CommanderExpDialog.closeEvent()` 主动 `emit dataRefreshed`，紧接着 `QDialog` 又发
`finished`，两个槽都调用 `updateCommanderStats()`。

2 次刷新 × 3 次效率计算 = **6 次**，即 6 × 626 ≈ 3.76 s。

## 3. 修复内容

| # | 改动 | 位置 |
| --- | --- | --- |
| 1 | 等级基准按等级缓存（基准表运行期只读） | `CommanderService._level_exp_cache` |
| 2 | 指级效率结果缓存，快照写入（增/改/删）时失效 | `CommanderService._efficiency_cache` + `_invalidateEfficiencyCache()` |
| 3 | 关闭只在 `finished` 时刷新一次，`closeEvent` 不再重复发信号 | `CommanderExpDialog` |
| 4 | 魔方 / 红尖尖卡改用 `getCardView()`：文本与提示共用一次结余扫描 | `ResourceService.getCardView()` + `StatisticsPanel.updateResourceStats()` |

## 5. 仍然存在、本次未改的开销

### 5.1 舰娘管理面板 181 ms（`ShipManagementPanel.refreshData`）

```
CodexOathPanel.refreshData   86.85 ms
AwakenPanel.refreshData      84.30 ms
LimitBreakPanel.refreshData   8.35 ms
CodexUnlockPanel.refreshData  2.42 ms
```

两处大头都不是数据库慢：

| 调用 | 耗时 | 说明 |
| --- | --- | --- |
| `AwakenService.getAwakenableShips()` | 11.2 ms | 返回 792 条 |
| `AwakenPanel.refreshData` 其余部分 | ≈ 74 ms | 逐条 `QComboBox.addItem(792 次)` |
| `CodexOathService.getOathableShips()` | 10.3 ms | 返回 815 条 |
| `CodexOathPanel.refreshData` 其余部分 | ≈ 77 ms | 逐条 `QComboBox.addItem(815 次)` |

即 **90% 的时间花在给下拉框逐条塞 800 项**，每次 `addItem` 都会触发模型/界面更新。

### 5.2 `StatisticsService.getAllStatistics()` 32 ms

看板其余统计（解锁率 / 誓约 / TP / 布林 / 剩余练级）在一次调用里聚合，
目前 32 ms，占数据看板刷新的近 40%。

### 5.3 每次查询新建 SQLite 连接

启动到首屏共 **78 次建连 / 41 ms**，平均 0.5 ms。单次不贵，但放大到 524 次（旧代码）
就是半秒级；后续新增「按行查询」的逻辑要避免这个模式。

## 6. 建议的后续优化（按收益排序）

1. **下拉框批量填充**：两个面板改用 `QComboBox.addItems([...])` 并配合
   `setUpdatesEnabled(False)`，或在初始化时一次性 `setModel`；预计 181 ms → 40 ms 左右；
2. **看板统计合并查询**：`getAllStatistics` 里的多段统计可合并为更少的聚合 SQL；
3. **连接复用**：`DatabaseConnection` 目前每次查询都 `sqlite3.connect`，可改为线程内的
   长连接（需配合 `setDbPath` 的失效逻辑与测试隔离）；
4. **避免行级查询**：任何"每条记录查一次"的写法都要提前按集合批量取（本次问题的根因）。
